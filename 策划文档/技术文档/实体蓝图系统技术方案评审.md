# 实体蓝图系统技术方案评审

## 1. 评审结论

建议引入“实体模型与实体蓝图分离”的设计，但分两阶段实施：

- 第一阶段：先拆分玩家出生点与玩家运行本体，确保编辑器预览与游戏渲染职责明确。
- 第二阶段：建立蓝图注册、挂载、参数配置和运行时实例化机制，支持玩家、敌人、触发器。

该方案适合当前项目，但不建议直接把动态函数、JavaScript 代码或完整运行时对象写入关卡 JSON。蓝图数据只保存蓝图 ID 和参数，动态计算函数由代码注册表提供。

推荐结构：

```text
实体数据
├── 编辑器模型：位置、尺寸、配置、蓝图挂载信息
├── 运行时实例：实体状态、动画状态、碰撞状态
└── 蓝图定义：绘制函数、更新函数、输入处理、碰撞处理
```

## 2. 需求理解

### 2.1 玩家出生点与玩家本体拆分

当前编辑器中的“玩家出生点”实际承担两个职责：

- 编辑器中显示玩家初始位置。
- 游戏开始时作为玩家本体的渲染位置。

调整后：

```text
编辑器模式
└── 玩家出生点：仅显示蓝色位置标记

游戏模式
└── 玩家实体：从出生点创建，使用玩家本体蓝图进行实际渲染
```

蓝色出生点不是玩家实体，也不挂载玩家本体蓝图。它只是关卡中的出生位置配置。

### 2.2 蓝图页签

在“实体工具”下新增“蓝图”页签，用于：

- 查看可用蓝图。
- 查看蓝图支持的实体类型。
- 配置蓝图参数。
- 将蓝图挂载到实体。
- 查看当前实体已挂载的蓝图。
- 后续扩展蓝图预览和调试。

### 2.3 当前考虑的可挂载实体类型

| 实体类型 | 是否支持 | 说明 |
|---|---:|---|
| 玩家 | 是 | 游戏开始时由出生点创建玩家实例 |
| 敌人 | 是 | 每个敌人实体可独立挂载蓝图 |
| 触发器 | 是 | 触发器可使用绘制和动态计算逻辑 |
| 墙体 | 暂不支持 | 当前保持纯几何碰撞实体 |
| 出生点 | 否 | 出生点是编辑器位置标记，不是运行时实体 |
| 子弹 | 暂不作为编辑器实体 | 由玩家或敌人蓝图运行时生成 |

## 3. 当前实现现状

### 3.1 玩家

当前玩家运行时对象在 `src/game-scene.js` 中由 `l.spawn` 初始化，并使用简单圆形绘制。后续玩家本体美术方案已经定义了：

- 正六边形主体。
- 黑色 Y 型内部结构。
- 多层圆环。
- 武器圆环和旋转小球。
- 护盾。
- 射击和动态动画。

这些内容属于运行时蓝图能力，不应继续直接堆在场景的通用 `draw()` 中。

### 3.2 敌人

当前关卡只保存敌人位置：

```json
{
  "x": 730,
  "y": 130
}
```

敌人运行时状态在场景中临时扩展 `r`、`alive` 等字段。后续可在敌人关卡数据中增加蓝图挂载信息。

### 3.3 触发器

当前状态模型中尚未定义触发器数据。需要新增触发器实体结构和编辑工具，但不建议和蓝图注册机制同时一次性完成全部触发器玩法。

### 3.4 现有编辑器

当前 `index.html` 的实体工具包含：

- 选择 / 移动。
- 墙体。
- 敌人。
- 玩家出生点。
- 橡皮擦。

建议保留这些基础实体工具，并新增独立的蓝图页签，而不是把蓝图 ID 直接混入工具按钮。

## 4. 核心设计原则

### 4.1 数据与行为分离

关卡 JSON 保存“实体是什么”和“挂载了什么蓝图”，不保存函数实现：

```json
{
  "type": "enemy",
  "x": 730,
  "y": 130,
  "blueprint": {
    "id": "enemy-basic",
    "version": 1,
    "params": {
      "color": "#e85b6e",
      "speed": 35
    }
  }
}
```

蓝图函数由代码注册：

```js
const blueprintRegistry = {
  'player-default': playerBlueprint,
  'enemy-basic': enemyBasicBlueprint,
  'trigger-area': triggerAreaBlueprint
};
```

不能从 JSON 动态执行字符串函数，避免安全风险、调试困难和存档不可控。

### 4.2 编辑器模型与运行时模型分离

编辑器模型：

```js
{
  id: 'enemy-1',
  type: 'enemy',
  x: 730,
  y: 130,
  blueprint: {
    id: 'enemy-basic',
    version: 1,
    params: {}
  }
}
```

运行时模型：

```js
{
  ...entity,
  blueprintInstance,
  alive: true,
  velocity: { x: 0, y: 0 },
  runtime: {}
}
```

运行时状态不能回写关卡配置，除非明确执行“保存编辑结果”。

### 4.3 蓝图负责行为，不负责实体身份

实体负责：

- 唯一 ID。
- 类型。
- 位置。
- 基础几何数据。
- 蓝图挂载信息。

蓝图负责：

- 初始化运行时状态。
- Canvas/Phaser Graphics 绘制。
- 每帧动态计算。
- 输入处理。
- 射击、动画和护盾逻辑。
- 碰撞或触发响应。
- 生命周期事件。

## 5. 数据结构设计

### 5.1 蓝图定义

建议定义统一蓝图接口：

```js
{
  id: 'player-default',
  name: '默认玩家本体',
  version: 1,
  supportedTypes: ['player'],
  defaults: {},
  schema: {},
  create(context, entity, params) {},
  update(context, runtime, dt) {},
  draw(context, runtime, graphics) {},
  destroy(context, runtime) {}
}
```

字段说明：

| 字段 | 说明 |
|---|---|
| `id` | 蓝图唯一 ID |
| `name` | 编辑器显示名称 |
| `version` | 蓝图版本，用于兼容和迁移 |
| `supportedTypes` | 可挂载实体类型 |
| `defaults` | 默认参数 |
| `schema` | 参数编辑和校验描述 |
| `create` | 创建运行时实例 |
| `update` | 每帧更新 |
| `draw` | Canvas 矢量绘制 |
| `destroy` | 销毁和清理资源 |

### 5.2 蓝图挂载结构

实体统一使用：

```js
blueprint: {
  id: 'player-default',
  version: 1,
  params: {}
}
```

如果一个实体后续需要多个蓝图，例如行为蓝图、表现蓝图、受击蓝图，可扩展为：

```js
blueprints: [
  {
    slot: 'visual',
    id: 'player-default',
    version: 1,
    params: {}
  },
  {
    slot: 'behavior',
    id: 'player-shooter',
    version: 1,
    params: {}
  }
]
```

第一阶段建议只支持一个主蓝图字段，保留后续扩展为多槽位蓝图的可能，避免过早引入组合调度复杂度。

### 5.3 玩家出生点数据

出生点继续保持简单结构：

```json
{
  "spawn": {
    "x": 130,
    "y": 300
  }
}
```

出生点不增加：

- `blueprint`。
- `runtime`。
- 玩家本体美术参数。
- 玩家战斗状态。

游戏开始时：

```text
读取 spawn
  ↓
创建 player 实体
  ↓
挂载 player-default 蓝图
  ↓
创建玩家运行时状态
  ↓
使用蓝图绘制玩家本体
```

### 5.4 敌人数据

兼容现有敌人数据，并允许挂载蓝图：

```json
{
  "id": "enemy-1",
  "x": 730,
  "y": 130,
  "blueprint": {
    "id": "enemy-basic",
    "version": 1,
    "params": {
      "speed": 35,
      "color": "#e85b6e"
    }
  }
}
```

旧数据无 `id` 或 `blueprint` 时由 `normalizeLevel()` 补默认值：

```js
{
  id: `enemy-${index + 1}`,
  blueprint: {
    id: 'enemy-basic',
    version: 1,
    params: {}
  }
}
```

### 5.5 触发器数据

建议新增：

```json
{
  "id": "trigger-1",
  "type": "trigger",
  "x": 400,
  "y": 300,
  "w": 120,
  "h": 80,
  "blueprint": {
    "id": "trigger-area",
    "version": 1,
    "params": {
      "event": "start-wave",
      "once": true
    }
  }
}
```

第一阶段触发器只需要支持矩形区域和进入事件，不先实现复杂条件树。

## 6. 蓝图运行时架构

### 6.1 模块划分

建议新增以下模块：

```text
src/blueprints/
├── registry.js
├── types.js
├── player-default.js
├── enemy-basic.js
└── trigger-area.js

src/blueprint-runtime.js
```

职责：

| 模块 | 职责 |
|---|---|
| `registry.js` | 注册和查询蓝图 |
| `types.js` | 蓝图接口和实体类型常量 |
| `player-default.js` | 玩家本体矢量美术、武器、护盾、射击 |
| `enemy-basic.js` | 基础敌人绘制、移动、受击 |
| `trigger-area.js` | 触发器区域绘制和进入事件 |
| `blueprint-runtime.js` | 创建实例、更新实例、绘制实例、销毁实例 |

### 6.2 运行时上下文

蓝图函数接收受控上下文：

```js
const context = {
  time,
  delta,
  input,
  level,
  scene,
  spawnBullet,
  emitEvent,
  queryEntities
};
```

蓝图不应直接依赖整个 `state` 或任意修改场景内部字段。所有跨实体操作通过上下文 API 完成，减少模块耦合。

### 6.3 生命周期

```text
挂载蓝图
  ↓
resolveBlueprint(id)
  ↓
校验 supportedTypes
  ↓
合并 defaults 和 params
  ↓
blueprint.create()
  ↓
每帧 blueprint.update()
  ↓
blueprint.draw()
  ↓
实体销毁时 blueprint.destroy()
```

缺少蓝图、类型不匹配或版本不兼容时，运行时应使用明确的错误状态，不执行未定义函数。

## 7. 玩家本体蓝图方案

玩家本体美术方案应迁移到：

```text
src/blueprints/player-default.js
```

蓝图负责：

- 正六边形主体绘制。
- 黑色 Y 型结构绘制。
- 主体多层圆环绘制。
- 武器圆环绘制。
- 白色小球旋转。
- 左键长按射击。
- 小球减速与松开反向旋转。
- 子弹拖尾颜色和行动轨迹。
- 右键护盾显示。
- 护盾方向跟随鼠标。
- 护盾防御判定。

玩家出生点只负责提供：

```js
{ x, y }
```

不负责调用任何玩家绘制函数。

## 8. 编辑器交互设计

### 8.1 实体工具页签

保留实体基础工具：

```text
实体工具
├── 选择 / 移动
├── 墙体
├── 敌人
├── 玩家出生点
└── 橡皮擦
```

“玩家出生点”按钮的说明应明确为：

```text
仅设置玩家进入游戏时的初始位置
```

编辑器中只绘制蓝色圆点或十字标记，不绘制玩家本体美术。

### 8.2 蓝图页签

在实体工具区域增加页签：

```text
[实体工具] [蓝图]
```

蓝图页签内容建议：

```text
蓝图
├── 当前选中实体：敌人-1
├── 实体类型：敌人
├── 已挂载蓝图：基础敌人
├── 蓝图版本：1
├── 蓝图参数
│   ├── 移动速度
│   ├── 颜色
│   └── 生命值
└── [应用] [移除]
```

如果未选中实体：

```text
请选择可挂载蓝图的实体
```

如果选中出生点：

```text
玩家出生点不是可挂载蓝图的运行时实体
```

### 8.3 蓝图列表过滤

蓝图列表根据当前实体类型过滤：

```text
选中玩家   → 显示 supportedTypes 包含 player 的蓝图
选中敌人   → 显示 supportedTypes 包含 enemy 的蓝图
选中触发器 → 显示 supportedTypes 包含 trigger 的蓝图
选中出生点 → 不显示可挂载蓝图
```

### 8.4 参数编辑

蓝图参数由 `schema` 驱动，不为每个蓝图手工写一套 UI：

```js
schema: {
  speed: { type: 'number', label: '移动速度', min: 0, max: 300 },
  color: { type: 'color', label: '颜色' }
}
```

第一版支持：

- `number`。
- `color`。
- `boolean`。
- `select`。

暂不支持脚本输入、表达式输入和自定义函数输入。

## 9. 绘制与编辑模式边界

### 9.1 编辑模式

编辑模式绘制：

- 墙体。
- 敌人编辑器占位图形或蓝图静态预览。
- 蓝色玩家出生点标记。
- 触发器边界。
- 选中框和辅助线。

玩家出生点不绘制完整玩家本体，避免编辑器将位置标记误认为运行时实体。

### 9.2 游戏模式

游戏模式绘制：

- 根据 `spawn` 创建玩家实体。
- 通过玩家蓝图绘制完整玩家本体。
- 根据敌人实体蓝图绘制敌人。
- 根据触发器蓝图绘制触发器或仅保留必要表现。
- 不绘制蓝色出生点编辑器标记。

## 10. 兼容迁移方案

### 10.1 旧墙体数据

墙体继续沿用现有模型，不自动挂载蓝图。

### 10.2 旧敌人数据

旧敌人只有 `x/y` 时，归一化为：

```js
{
  ...enemy,
  id: enemy.id || `enemy-${index + 1}`,
  blueprint: enemy.blueprint || {
    id: 'enemy-basic',
    version: 1,
    params: {}
  }
}
```

### 10.3 旧出生点数据

旧 `spawn` 数据保持不变：

```json
"spawn": { "x": 130, "y": 300 }
```

不能把 `spawn` 自动转换成 `player` 实体写回关卡，以免改变现有关卡数据结构和编辑器操作方式。

### 10.4 蓝图版本

蓝图版本用于处理未来参数变化：

```js
blueprint: {
  id: 'player-default',
  version: 1,
  params: {}
}
```

蓝图升级时由迁移函数处理：

```js
migrateBlueprint(blueprintConfig, targetVersion)
```

## 11. 方案优点

- 玩家出生点和玩家本体职责清晰。
- 玩家本体美术与场景控制逻辑解耦。
- 敌人可以复用同一套蓝图运行机制。
- 触发器可以使用动态计算函数。
- 蓝图参数可配置、可保存、可版本化。
- 新增蓝图不需要修改关卡数据结构。
- 不需要在 JSON 中执行任意代码。
- 编辑器可根据实体类型自动过滤蓝图。
- 后续可扩展多蓝图槽位、蓝图预览和蓝图库。

## 12. 风险与评审意见

### 12.1 蓝图职责过重

如果一个蓝图同时负责移动、绘制、射击、碰撞、掉落和任务逻辑，后期会难以维护。

建议：

- 第一阶段一个实体只挂载一个主蓝图。
- 蓝图内部按行为函数拆分。
- 后续稳定后再引入表现、行为、触发响应等多槽位蓝图。

### 12.2 编辑器预览与运行时预览不一致

玩家本体包含旋转、护盾、武器小球等动态表现。编辑器如果完整运行蓝图，可能引入输入和状态问题。

建议：

- 编辑器只显示出生点蓝色标记。
- 蓝图页签提供静态缩略预览或独立预览区域。
- 游戏预览才运行完整玩家蓝图。

### 12.3 蓝图参数失效

蓝图参数可能因蓝图版本变化而失效。

建议：

- 保存 `id + version + params`。
- 加载时校验参数并补默认值。
- 不识别的参数忽略，不阻止整个关卡加载。
- 蓝图不存在时显示明确错误，并提供默认占位表现。

### 12.4 蓝图之间互相修改状态

蓝图直接访问其他蓝图实例会造成隐式耦合。

建议：

- 使用 `emitEvent()` 发布事件。
- 使用 `queryEntities()` 查询实体。
- 通过运行时管理器统一修改实体生命周期。

### 12.5 当前 Phaser Graphics 绘制方式

玩家本体全部使用 `Graphics` 每帧重绘，符合当前项目规模。但如果未来实体和子弹数量大幅增加，应评估：

- 是否拆分静态和动态图层。
- 是否缓存不变的蓝图图形。
- 是否为大量敌人改用池化对象。

当前阶段无需提前引入复杂渲染优化。

## 13. 推荐实施计划

### 阶段一：玩家出生点与玩家实体解耦

- 保留 `spawn` 为关卡位置数据。
- 编辑模式只显示蓝色出生点。
- 游戏开始时由 `spawn` 创建玩家运行时对象。
- 将玩家本体绘制函数从场景 `draw()` 中拆出。
- 新增 `player-default` 蓝图。

完成标准：出生点只显示编辑器位置，游戏中只渲染玩家本体。

### 阶段二：蓝图注册和运行时管理

- 新增蓝图注册表。
- 新增蓝图查找和类型校验。
- 新增蓝图实例生命周期。
- 让玩家蓝图接入统一运行时。

完成标准：玩家本体不再由场景硬编码绘制，蓝图可独立更新和绘制。

### 阶段三：敌人蓝图

- 为敌人增加 `id` 和蓝图挂载配置。
- 增加 `enemy-basic` 蓝图。
- 旧敌人自动挂载默认敌人蓝图。
- 蓝图页签支持敌人选择和参数编辑。

完成标准：不同敌人可选择不同蓝图和参数。

### 阶段四：触发器蓝图

- 增加触发器数据结构。
- 增加触发器实体工具。
- 增加 `trigger-area` 蓝图。
- 支持进入区域触发事件。

完成标准：触发器可以挂载蓝图并在运行时响应事件。

### 阶段五：蓝图编辑器完善

- 蓝图页签增加静态预览。
- 增加参数 schema 自动生成表单。
- 增加蓝图版本提示。
- 增加缺失蓝图和参数校验。
- 增加蓝图调试信息。

## 15. 验收标准

1. 编辑器中的蓝色玩家出生点只表示出生位置。
2. 蓝色出生点不再渲染玩家完整本体美术。
3. 游戏开始后玩家从出生点创建，并使用玩家蓝图渲染。
4. 玩家本体动态逻辑不依赖出生点绘制逻辑。
5. 实体工具下存在独立蓝图页签。
6. 蓝图列表能够按照实体类型过滤。
7. 玩家、敌人可以挂载对应蓝图。
8. 触发器数据和蓝图接口预留完成。
9. 出生点不能挂载蓝图。
10. 蓝图配置保存为 ID、版本和参数，不保存函数源码。
11. 旧敌人数据可以自动挂载默认敌人蓝图。
12. 缺失或不兼容蓝图时不会导致整个关卡加载失败。
13. 玩家、敌人、触发器蓝图可以独立更新和绘制。
14. 蓝图参数修改后可保存并重新加载。
15. 墙体和现有编辑器功能无回归。

## 16. 暂不实现范围

第一版暂不实现：

- 蓝图可视化节点编辑器。
- JSON 中执行自定义脚本。
- 一个实体挂载多个行为蓝图。
- 蓝图之间直接互相调用。
- 在线蓝图热更新。
- 蓝图市场或外部资源导入。
- 复杂触发器条件树。
- 蓝图自动生成完整编辑器 UI。
- 墙体和子弹作为可编辑蓝图实体。

## 17. 最终建议

该需求建议立项，但必须先完成“出生点与玩家实体解耦”，再引入通用蓝图系统。

推荐第一版最小闭环：

```text
spawn
  ↓
创建 player 实体
  ↓
挂载 player-default
  ↓
blueprint.create()
  ↓
blueprint.update()
  ↓
blueprint.draw()
```

完成玩家闭环后，再将同一套注册表和生命周期机制复用到敌人，最后接入触发器。这样可以控制改造范围，避免在当前编辑器基础较薄的情况下同时引入复杂实体系统。
