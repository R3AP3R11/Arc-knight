# 流程编排技术方案

## 1. 文档目的

本文档定义游戏主界面、游戏流程、教程流程之间的技术关系，并规划编辑器流程配置功能的迭代方向。

目标结构：

```text
主界面
├── 游戏入口 → 游戏流程
└── 教程入口 → 教程流程
```

游戏流程与教程流程独立维护、独立运行。第一阶段只支持线性流程，不引入分支、条件节点和 DAG 调度。

## 2. 当前实现现状

当前流程配置结构为：

```json
{
  "start": "level-1",
  "levels": ["level-2", "level-3"]
}
```

当前已具备：

- 编辑器中选择起始关卡。
- 追加和删除流程关卡。
- 通过 `/api/flow` 读写流程配置。
- 流程配置持久化到 `data/flow.json`。

当前缺口：

- 只有一条流程，无法区分游戏流程和教程流程。
- `flowIndex` 尚未接入实际执行逻辑。
- 游戏运行时只加载单个 `state.level`。
- 当前关卡结束后不会自动进入下一关。
- 没有流程完成、失败和进度保存状态。
- 没有入口节点、末节点和资源合法性校验。

因此，当前功能属于流程配置雏形，尚未形成完整的流程执行链路。

## 3. 目标架构

### 3.1 模块划分

```text
主界面
└── FlowRunner：启动流程、推进节点、结束流程
    ├── GameNodeExecutor：加载并运行游戏关卡
    └── TutorialNodeExecutor：加载并运行教程内容
```

`FlowRunner` 只负责流程控制，不处理具体游戏或教程内容。游戏和教程节点分别由对应执行器负责加载、运行和上报完成结果。

### 3.2 运行链路

```text
主界面
  ├─ 点击“开始游戏”
  │    └─ startFlow("game")
  │         └─ 读取 game.entry
  │              └─ 加载游戏节点
  │                   └─ 节点完成
  │                        ├─ 有下一节点：推进并加载下一节点
  │                        └─ 无下一节点：游戏流程完成
  └─ 点击“教程”
       └─ startFlow("tutorial")
            └─ 读取 tutorial.entry
                 └─ 加载教程节点
                      └─ 节点完成
                           ├─ 有下一节点：推进并加载下一节点
                           └─ 无下一节点：教程流程完成并返回主界面
```

## 4. 流程配置数据结构

建议将现有单流程结构升级为多流程结构：

```json
{
  "version": 2,
  "flows": {
    "game": {
      "name": "游戏流程",
      "entry": "level-1",
      "nodes": [
        {
          "id": "level-1",
          "type": "level",
          "target": "level-1"
        },
        {
          "id": "level-2",
          "type": "level",
          "target": "level-2"
        }
      ]
    },
    "tutorial": {
      "name": "教程流程",
      "entry": "tutorial-1",
      "nodes": [
        {
          "id": "tutorial-1",
          "type": "tutorial",
          "target": "tutorial-1"
        }
      ]
    }
  }
}
```

### 4.1 字段定义

| 字段 | 类型 | 说明 |
|---|---|---|
| `version` | number | 配置版本号，用于后续迁移 |
| `flows.game` | object | 游戏流程配置 |
| `flows.tutorial` | object | 教程流程配置 |
| `name` | string | 流程显示名称 |
| `entry` | string | 流程入口节点 ID |
| `nodes` | array | 按执行顺序排列的节点列表 |
| `nodes[].id` | string | 节点唯一 ID |
| `nodes[].type` | string | 节点类型，第一阶段为 `level` 或 `tutorial` |
| `nodes[].target` | string | 对应的关卡或教程资源 ID |

第一阶段使用数组顺序表达节点关系，不额外保存 `next` 字段，避免配置产生双重来源。后续支持分支时，再扩展节点连接关系。

## 5. 运行时状态

在现有 `state` 中增加流程运行上下文：

```js
flowRuntime: {
  type: 'game',
  index: 0,
  currentNodeId: 'level-1',
  status: 'running'
}
```

### 5.1 状态字段

| 字段 | 说明 |
|---|---|
| `type` | 当前运行流程：`game` 或 `tutorial` |
| `index` | 当前节点在流程数组中的索引 |
| `currentNodeId` | 当前节点 ID |
| `status` | `idle`、`running`、`completed` 或 `failed` |

### 5.2 节点推进逻辑

```text
completeCurrentNode()
  ├─ 获取当前流程和当前索引
  ├─ 判断是否存在下一节点
  ├─ 存在下一节点：index + 1，更新 currentNodeId，加载节点
  └─ 不存在下一节点：status = completed，进入流程完成处理
```

节点失败时，第一阶段只提供：

- 重试当前节点。
- 返回主界面。
- 游戏流程和教程流程分别处理失败结果。

暂不加入自动重试次数、分支回退和跨流程跳转。

## 6. 编辑器功能迭代

### 6.1 流程类型切换

流程配置区域增加：

```text
[游戏流程] [教程流程]
```

切换后只编辑对应流程，避免游戏关卡和教程节点混在同一列表中。

### 6.2 节点编排

每条流程支持：

- 设置入口节点。
- 添加节点。
- 删除节点。
- 上移节点。
- 下移节点。
- 拖拽排序。
- 编辑节点名称。
- 选择节点类型和目标资源。
- 预览当前流程。
- 保存当前流程。

列表示例：

```text
1  [入口] 教程一       ↑ ↓ 删除
2         教程二       ↑ ↓ 删除
3  [结束] 教程完成     ↑ ↓ 删除
```

### 6.3 保存前校验

保存前必须校验：

- 流程至少包含一个节点。
- `entry` 必须存在于节点列表。
- 节点 ID 不能为空。
- 节点 ID 不能重复。
- 节点目标资源不能为空。
- 节点目标资源必须存在。
- 游戏流程节点类型必须匹配游戏资源。
- 教程流程节点类型必须匹配教程资源。

校验失败时显示具体节点和错误原因，不覆盖已有有效配置。

## 7. 服务端与文件存储

### 7.1 配置文件

建议将配置文件升级为：

```text
data/flows.json
```

服务端接口建议保持统一：

| 方法 | 路径 | 作用 |
|---|---|---|
| `GET` | `/api/flow` | 获取全部流程配置 |
| `POST` | `/api/flow` | 覆盖保存全部流程配置 |

为降低改造成本，也可以暂时继续使用 `data/flow.json`，但内容升级为 `version + flows` 结构。

### 7.2 玩家进度

流程配置与玩家进度分离：

```text
data/
├── flows.json
└── progress.json
```

进度结构：

```json
{
  "game": {
    "currentNodeId": "level-2",
    "index": 1,
    "status": "running"
  },
  "tutorial": {
    "currentNodeId": "tutorial-1",
    "index": 0,
    "status": "completed"
  }
}
```

编辑器保存流程时不得修改玩家进度。流程配置发生变更后，运行时应校验旧进度对应节点是否仍存在；不存在时回退到流程入口。

## 8. 代码改造计划

| 文件 | 改造内容 |
|---|---|
| `src/state.js` | 将单流程状态升级为双流程配置，增加 `flowRuntime` |
| `src/main.js` | 加载双流程、切换流程类型、启动游戏和教程入口 |
| `src/ui.js` | 渲染流程切换、节点排序、入口/结束标识和校验信息 |
| `src/game-scene.js` | 关卡完成后通知流程推进，不再无条件重启当前关卡 |
| `server.js` | 支持新流程配置结构和配置校验 |
| `src/flow-runner.js` | 新增流程启动、节点推进、完成、失败处理 |
| 主界面模块 | 新增游戏入口、教程入口和流程状态展示 |
| `data/flow.json` 或 `data/flows.json` | 保存双流程配置 |
| `data/progress.json` | 保存运行进度 |

## 9. 分阶段实施

### 阶段一：数据结构升级

- 增加 `version`。
- 将单流程改为 `game` 和 `tutorial` 两条流程。
- 保留线性数组结构。
- 增加旧配置迁移逻辑。
- 增加基础保存校验。

完成标准：旧流程配置可迁移，新编辑器可分别保存两条流程。

### 阶段二：编辑器编排能力

- 增加流程类型切换。
- 增加上移、下移和拖拽排序。
- 增加入口节点和结束节点标识。
- 增加资源存在性校验。
- 增加流程预览。

完成标准：策划可以独立配置游戏流程和教程流程，并能在保存前发现错误。

### 阶段三：运行时流程推进

- 新增 `FlowRunner`。
- 主界面通过流程类型启动运行。
- 节点完成后自动进入下一节点。
- 末节点触发流程完成。
- 支持重试当前节点和返回主界面。

完成标准：游戏和教程均可按配置顺序连续运行，不再重复加载当前节点。

### 阶段四：主界面接入

- 增加游戏入口。
- 增加教程入口。
- 教程完成后返回主界面。
- 游戏完成后进入结算或返回主界面。
- 展示流程完成状态和继续入口。

完成标准：主界面、教程流程、游戏流程形成完整闭环。

### 阶段五：进度与调试能力

- 保存当前节点进度。
- 支持继续游戏。
- 支持重置教程。
- 支持跳过已完成教程。
- 调试模式支持跳转指定节点。

完成标准：刷新或重新进入后可以恢复流程状态，开发调试可以快速定位节点。

## 10. 暂不实现范围

第一版不实现：

- 条件分支。
- 多条件解锁。
- DAG 流程图。
- 节点并发执行。
- 自动重试策略。
- 跨流程跳转。
- 复杂奖励和结算节点。

这些能力待线性流程稳定后，根据实际需求扩展。

## 11. 验收标准

1. 主界面可以分别进入游戏和教程。
2. 编辑器可以分别配置游戏流程和教程流程。
3. 两条流程互不污染配置和进度。
4. 流程入口始终有效。
5. 节点按配置顺序执行。
6. 当前节点完成后自动加载下一节点。
7. 末节点完成后触发对应流程完成逻辑。
8. 节点失败时可以重试或返回主界面。
9. 非法配置无法保存。
10. 刷新或重新进入后，流程进度可以正确恢复或安全回退到入口。
11. 旧版单流程配置可以迁移到新版结构。
